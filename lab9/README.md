## 2. API клиента (задание 1)

| Функция | Назначение |
|---|---|
| `GetErrorMsgText(code)` | текст ошибки Winsock2 по коду |
| `PrintError(operation, code)` | печать ошибки в формате «операция: текст» |
| `GetLocalBroadcastAddress()` | направленный широковещательный адрес активного адаптера |
| `FindServer(callSign, udpPort, tcpPort, server, timeoutMs)` | найти сервер по позывному широковещанием, вернуть IP и заполнить адрес для TCP |
| `FindServerByName(hostname, tcpPort, server, timeoutMs)` | найти сервер по имени хоста (`getaddrinfo`, IPv4) и подключиться по TCP; общий бюджет времени — `timeoutMs`; `false`, если имя не разрешилось, адреса недоступны или вышло время |
| `ConnectToServer(server)` | TCP-подключение к найденному серверу, установка `SO_RCVTIMEO` |
| `SendAllBytes(s, data, bytes)` | передать буфер целиком: цикл `send` до конца, частичная отправка не считается успехом |
| `SendText(s, text)`, `ReceiveText(s, buf, size)` | передача и приём строки с завершающим нулём. Приём — точный NUL-фрейминг с буфером на сокет: частичные `recv` склеиваются, несколько фреймов в одном пакете читаются по одному; EOF среди фрейма, таймаут, обрыв, фрейм без NUL свыше 1 МБ — отказ (`SOCKET_ERROR`) |
| `ParseIntStrict(text, value)` | строгий разбор целого: только знак и цифры, без переполнения (`"12abc"`, `""` — отказ) |
| `SendRequest(s, code)` | отправить код запроса (`echo`/`time`/`rand`) |
| `RequestEcho`, `RequestTime`, `RequestRand` | одна транзакция соответствующего типа |
| `SendInvalidRequest(s, answer, size)` | заведомо некорректный запрос для проверки реакции сервера |
| `ElapsedSeconds(startTick)` | время сеанса по `GetTickCount` |

Протокол (совпадает с сервером из ЛР8):

| Код запроса | Обмен | Признак завершения |
|---|---|---|
| `echo` | клиент шлёт текст, сервер возвращает его без изменений | клиент закрывает сокет |
| `time` | клиент шлёт `time`, сервер отвечает `дд.мм.гггг/чч:мм:сс` | любая строка, отличная от `time` |
| `rand` | клиент шлёт `rand`, сервер отвечает 4 байтами (`int`, формат Intel) | любая строка, отличная от `rand` |
| любой другой | сервер отвечает `ErrorInquiry` и разрывает соединение | — |

## 3. Неблокирующий поиск сервера (задание 2)

Отличие от `GetServer` из ЛР4: там `recvfrom` блокировал поток до прихода отклика или таймаута `SO_RCVTIMEO`. Здесь сокет переведён в неблокирующий режим, и функция сама управляет ожиданием:

1. `socket(SOCK_DGRAM)` + `SO_BROADCAST`;
2. `ioctlsocket(s, FIONBIO, &1)` — режим без блокировки;
3. `sendto` позывного на широковещательный адрес;
4. цикл до `timeoutMs`: `recvfrom` → если `WSAEWOULDBLOCK`, спать 20 мс и повторять; если пришёл позывной — вернуть адрес сервера; если чужая строка — продолжать;
5. по истечении таймаута — `false` (сервер не найден).

Практическая выгода: функция не «зависает» на одном вызове ядра, время ожидания задаётся параметром, а поток остаётся управляемым (можно вставлять проверки, обновлять интерфейс, реагировать на команды).

## 4. Клиентские программы (задание 3)

| Программа | Что делает | Аргументы |
|---|---|---|
| `ClientEcho` | находит сервер, шлёт `echo`, передаёт N сообщений с задержкой, сверяет эхо, затем отдельным подключением проверяет реакцию на некорректный запрос | широковещание: `[позывной] [UDP-порт] [TCP-порт] [сообщений] [задержка мс]`; по имени: `--dns <hostname> <tcpPort> [count] [delayMs]` |
| `ClientTime` | запрашивает дату-время N раз, затем отправляет строку, отличную от `time`, и проверяет завершение сеанса | широковещание: `[позывной] [UDP-порт] [TCP-порт] [запросов]`; по имени: `--dns <hostname> <tcpPort> [count]` |
| `ClientRand` | запрашивает случайные числа N раз (ровно 4 байта на ответ), затем завершает сеанс строкой, отличной от `rand` | широковещание: `[позывной] [UDP-порт] [TCP-порт] [запросов]`; по имени: `--dns <hostname> <tcpPort> [count]` |

Все три находят сервер широковещанием (IP), TCP-порт задаётся аргументом — так же, как в задании 3 практикума: «отыскав его IP-адрес с помощью широковещательных сообщений». Альтернативный режим `--dns` разрешает имя хоста через `getaddrinfo` и подключается по TCP; hostname не трактуется как UDP-позывной.

Надёжность сеанса: аргументы проверяются строго (порты 1..65535, количество >= 1, задержка >= 0 — иначе ненулевой код возврата 2); если получено меньше ответов, чем запрошено (обрыв сервера, таймаут, частичный ответ), программа завершается с кодом 1 и печатает точный счёт «корректных ответов X из N».

## 5. Результаты локальной проверки (Windows 11, MSVC 14.51, localhost)

Сервер: `ConcurrentServer.exe 9301 ServiceLibrary.dll \\.\pipe\TestConsole 9300 TestServer`.

| Проверка | Ожидание | Факт |
|---|---|---|
| `ClientEcho TestServer 9300 9301 5 50` | 5 корректных эхо | `корректных ответов 5 из 5, время сеанса 0.328 с` |
| `ClientEcho` с некорректным запросом | `ErrorInquiry` | `ответ на некорректный запрос: ErrorInquiry` |
| `ClientTime TestServer 9300 9301 3` | 3 ответа с датой | `26.10.2026/22:13:48` ×3, `3 из 3` |
| `ClientRand TestServer 9300 9301 3` | 3 числа | `29557, 28020, 6758`, `3 из 3` |
| три клиента одновременно | параллельное обслуживание | `ClientEcho 4 из 4`, `ClientTime 4 из 4`, `ClientRand 4 из 4` |
| неверный позывной `NoSuchServer` | сервер не найден | `ClientEcho: сервер не найден` |
| статистика сервера после прогона | счётчики | `подключений всего: 12, обслужено успешно: 12, отказов: 6, активных: 0` |

Дефект, найденный при этом прогоне: первый `ClientEcho` показывал `4 из 5`. Причина — сервер читал код запроса одним `recv`, и если клиент успевал отправить первое сообщение тем же пакетом, оно попадало в тот же буфер и терялось (строка кода всё равно совпадала, потому что `strcmp` останавливается на завершающем нуле). Исправлено в ЛР8: остаток буфера после кода запроса передаётся обслуживающему потоку в поле `pending`, и `EchoServer` отправляет его первым. После исправления — `5 из 5`.

```cmd
cl /nologo /EHsc /utf-8 /W3 lab9\ClientEcho\ClientEcho.cpp lab9\ClientApi\ClientApi.cpp /Fe:lab9\build\ClientEcho.exe
cl /nologo /EHsc /utf-8 /W3 lab9\ClientTime\ClientTime.cpp lab9\ClientApi\ClientApi.cpp /Fe:lab9\build\ClientTime.exe

cl /nologo /EHsc /utf-8 /W3 lab9\tests\ClientApiTests.cpp /Fe:lab9\build\ClientApiTests.exe
```

Каждый клиент содержит `#pragma comment(lib, "WS2_32.lib")`, поэтому проект, собранный из одного `ClientEcho.cpp`, линкуется без ручного добавления библиотеки в настройках компоновщика. Файл `ClientApi.cpp` всё равно должен входить в сборку: без него компоновщик не найдёт `FindServer`, `FindServerByName`, `ConnectToServer`, `SendText`, `ReceiveText` и остальные функции API.

`lab9\tests\ClientApiTests.cpp` — самодостаточный тестовый exe: он включает `ClientApi.cpp` напрямую и поднимает локальный TCP/UDP-пир в своём процессе. Прогон проверяет фрейминг (частичные и коалесцированные NUL-фреймы), `SendAll`, 4-байтовый `rand`, режим `--dns` через реальные exe клиентов, отказ при обрыве сервера и строгую валидацию аргументов. Тесты писались до исправлений: на старых исходниках 11 проверок падали (RED), на исправленных проходят все 16 (GREEN).

## 7. Вопросы для самопроверки

1. **Зачем клиенту API, а не прямой код в каждой программе?** Протокол и обработка ошибок живут в одном месте; три программы отличаются только сценарием, а не реализацией обмена (задание 1).
2. **Что даёт `ioctlsocket(FIONBIO)` в поиске сервера?** `recvfrom` не блокирует поток: функция сама решает, сколько ждать и что делать между попытками (задание 2, раздел 6.9).
3. **Почему широковещанием ищется только IP, а порт передаётся аргументом?** Широковещательный отклик приходит с UDP-порта ответчика, который не обязан совпадать с TCP-портом сервера; надёжнее знать порт заранее (как в задании 3 практикума).
4. **Как клиент понимает, что запрос некорректен?** Сервер отвечает строкой `ErrorInquiry` и закрывает соединение; клиент сверяет ответ и сообщает об отказе.
5. **Почему `time` и `rand` завершают сеанс по «не своей» строке?** Так задан протокол в таблице 7.9.4: обслуживающий поток читает сообщения, пока они равны коду запроса.
6. **Зачем `SO_RCVTIMEO` на клиентском сокете?** Чтобы ожидание ответа не было бесконечным: при сбое сервера клиент получит `WSAETIMEDOUT` и завершится с диагностикой.
7. **Как измерить максимальное время работы клиента?** `GetTickCount` до и после сеанса (`ElapsedSeconds`), как в требовании «проверять на максимальное время работы».
8. **Что будет, если сервер не найден?** `FindServer` вернёт `false` после таймаута, программа сообщит «сервер не найден» и завершится с кодом 1.

## 8. Что не проверено

- Работа клиентов на другом компьютере (проверка на одной машине, локальный сегмент).
- Клиенты для команды `echo` с сообщением нулевой длины как отдельным сигналом завершения: сеанс завершается закрытием сокета.
