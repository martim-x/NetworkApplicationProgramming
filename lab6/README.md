# Лабораторная работа №6: Именованные каналы (Named Pipe) (ПР6)

Источник задания: практикум, раздел 7.7 «Работа с интерфейсом Named Pipe» (задания 1–8), глава 4 пособия «Интерфейс Named Pipe».

## 1. Состав работы

| Задание практикума | Файл | Что реализовано |
|---|---|---|
| 1, 3, 4, 5, 6 (сервер) | `ServerNP/ServerNP.cpp` | `CreateNamedPipe` + `ConnectNamedPipe`, `DisconnectNamedPipe`, цикл обслуживания клиентов, эхо `ReadFile`/`WriteFile`, счётчик сообщений и время обмена |
| 2, 4, 5, 6 (клиент) | `ClientNP/ClientNP.cpp` | `CreateFile`, `WriteFile`/`ReadFile`, обработка `ERROR_PIPE_BUSY` через `WaitNamedPipe`, локальное и сетевое имя канала |
| 7 | `ClientNPt/ClientNPt.cpp` | то же взаимодействие через `TransactNamedPipe` (транзакция = запись + чтение за один вызов) |
| 8 | `ClientNPct/ClientNPct.cpp` | то же через `CallNamedPipe` (подключение, одна транзакция, разрыв связи за один вызов) |
| сборка и запуск | `HELPER.md` | копипастные команды |

## 2. Сборка и запуск

Полные команды — в `HELPER.md`. Кратко: четыре консольных приложения, собираются компилятором MSVC (`cl /EHsc /utf-8`), линкуется `WS2_32.lib`.

Аргументы программ:

```
ServerNP.exe [имя канала]                  по умолчанию \\.\pipe\Tube
ClientNP.exe [имя канала] [сообщений]      по умолчанию \\.\pipe\Tube, количество спрашивается
ClientNPt.exe [имя канала] [транзакций]
ClientNPct.exe [имя канала] [транзакций]
```

Имя канала можно задавать тремя способами: короткое (`Tube` → `\\.\pipe\Tube`), полное локальное (`\\.\pipe\Tube`), сетевое (`\\ИМЯ_КОМПЬЮТЕРА\pipe\Tube`).

У именованных каналов нет портов: роль «порта» играет имя канала. Два сервера на одном компьютере — это два разных имени (`\\.\pipe\Test1`, `\\.\pipe\Test2`), и клиент попадает только в тот, чьё имя указал.

## 3. Протокол обмена

```
Сервер                                     Клиент
CreateNamedPipe(\\.\pipe\Tube)
ConnectNamedPipe (блокируется)
                                           CreateFile(\\.\pipe\Tube)
                                           WriteFile("Hello from ClientNP 001")
ReadFile  -> "Hello from ClientNP 001"
WriteFile -> "Hello from ClientNP 001"
                                           ReadFile -> эхо
                                           WriteFile("") — сообщение нулевой длины
ReadFile -> 0 байт / "\0" = конец сеанса
DisconnectNamedPipe
ConnectNamedPipe (следующий клиент)
```

Правила, заложенные в реализацию:

- канал открыт в режиме сообщений (`PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE`), поэтому одна запись = одно чтение, границы сообщений сохраняются;
- конец сеанса — сообщение нулевой длины (клиент пишет 1 байт `\0`), как в задании 5 (по аналогии с `ServerT`/`ClientT`);
- сервер не завершается при отключении клиента: ошибки `ERROR_BROKEN_PIPE`, `ERROR_NO_DATA`, `ERROR_PIPE_NOT_CONNECTED` считаются нормальным концом сеанса, после `DisconnectNamedPipe` сервер ждёт следующего клиента (задание 5 практикума №2 — «сервер может снова установить соединение с другим клиентом»);
- клиент при `ERROR_PIPE_BUSY` (все экземпляры заняты) вызывает `WaitNamedPipe` и повторяет `CreateFile`;
- `ClientNPt` перед `TransactNamedPipe` переводит свой дескриптор в режим чтения сообщениями через `SetNamedPipeHandleState`: без этого вызов падает с кодом 230 `ERROR_BAD_PIPE` — проверено фактически;
- клиент без запущенного сервера получает `ERROR_FILE_NOT_FOUND` (код 2) и завершается с кодом возврата 1 (задание 2).

## 4. Разбор по заданиям

**Задание 1.** Сервер создаёт канал `\\.\pipe\Tube` (`CreateNamedPipeA`), затем блокируется на `ConnectNamedPipe` — поток приостановлен до подключения клиента. После сеанса вызывается `DisconnectNamedPipe`. Функции обработки ошибок `GetErrorMsgText`/`SetErrorMsgText` построены по тому же принципу, что и в Winsock-лабораториях: код ошибки → текст на русском, любая нештатная ситуация → `throw`.

**Задание 2.** Клиент подключается через `CreateFileA(..., OPEN_EXISTING, ...)`. Запуск без сервера даёт `ERROR_FILE_NOT_FOUND`, текст выводится обработчиком ошибок.

**Задание 3.** Сервер и клиент на одном компьютере: сервер выходит из ожидания, обмен завершается, обе программы завершаются без ошибок.

**Задание 4.** Обмен реализован парой `WriteFile`/`ReadFile` в обе стороны (эхо).

**Задание 5.** Клиент передаёт последовательность сообщений `Hello from ClientNP xxx`, сервер возвращает их без изменения, клиент печатает полученное; количество сообщений задаётся аргументом или вводится с консоли; время обмена измеряется `clock()`.

**Задание 6.** Клиент поддерживает сетевой формат имени `\\ИМЯ_КОМПЬЮТЕРА\pipe\Tube` (имя компьютера — из `hostname`). На одной машине такой вызов работает и проверен; обмен между двумя компьютерами не проверялся (нет второй машины под рукой).

**Задание 7.** `ClientNPt` выполняет каждое сообщение одной транзакцией `TransactNamedPipe`.

**Задание 8.** `ClientNPct` выполняет каждое сообщение вызовом `CallNamedPipe`: каждый вызов — отдельное подключение, одна транзакция, разрыв связи. В журнале сервера это видно как отдельные сеансы по одному сообщению.

## 6. Отличие Named Pipe от сокетов

| Характеристика | Named Pipe | TCP | UDP |
|---|---|---|---|
| Адресация | имя `\\.\pipe\Имя` | IP + порт | IP + порт |
| Границы сообщений | да (`PIPE_TYPE_MESSAGE`) | нет | да |
| Установка соединения | `ConnectNamedPipe` / `CreateFile` | `connect` / `accept` | не нужна |
| Надёжность | гарантирована, порядок сохранён | гарантирована | нет гарантий |
| Параллельные клиенты | несколько экземпляров канала | `accept` + потоки | один сокет для всех |
| Область | один компьютер или сеть (SMB) | сеть | сеть |

## 7. Коды ошибок

| Код | Имя | Причина |
|---|---|---|
| 2 | `ERROR_FILE_NOT_FOUND` | канал с таким именем не создан (сервер не запущен) |
| 5 | `ERROR_ACCESS_DENIED` | нет прав доступа (ACL канала) |
| 109 | `ERROR_BROKEN_PIPE` | клиент закрыл канал, не завершив сеанс |
| 230 | `ERROR_BAD_PIPE` | `TransactNamedPipe` без режима чтения сообщениями |
| 231 | `ERROR_PIPE_BUSY` | все экземпляры заняты, нужен `WaitNamedPipe` |
| 232 | `ERROR_NO_DATA` | канал закрывается |
| 233 | `ERROR_PIPE_NOT_CONNECTED` | нет процесса на другом конце |
| 234 | `ERROR_MORE_DATA` | сообщение длиннее буфера чтения |
| 535 | `ERROR_PIPE_CONNECTED` | клиент подключился до `ConnectNamedPipe` (штатная ситуация) |

## 8. Вопросы для самопроверки

1. **`PIPE_TYPE_MESSAGE` и `PIPE_TYPE_BYTE`** — в режиме сообщений каждая запись читается одной операцией чтения, границы сохраняются; в байтовом режиме это поток, границы теряются, а `TransactNamedPipe`/`CallNamedPipe` требуют режима сообщений.
2. **Параллельное обслуживание нескольких клиентов** — нужно несколько экземпляров канала (`CreateNamedPipe` в цикле) и отдельный поток на каждый экземпляр (или IOCP). В этой работе создан один экземпляр с `PIPE_UNLIMITED_INSTANCES`, поэтому клиенты обслуживаются последовательно, а второй клиент ждёт (`ERROR_PIPE_BUSY` + `WaitNamedPipe`).
3. **`CreateFile` до запуска сервера** — возвращает `INVALID_HANDLE_VALUE` с кодом `ERROR_FILE_NOT_FOUND` (2).
4. **Передача дескриптора другому процессу** — через `DuplicateHandle` (или наследование дескриптора при `CreateProcess` с `bInheritHandles`), сам дескриптор канала между процессами не «пересылается».
5. **`\\.\pipe\Name` и `\\Server\pipe\Name`** — локальный и сетевой форматы имени: точка = текущий компьютер, `Server` = имя компьютера-сервера (SMB).
6. **`DisconnectNamedPipe`** — отключает текущего клиента и возвращает экземпляр в состояние ожидания; без него следующий `ConnectNamedPipe` не сработает.
7. **Преимущества перед TCP на localhost** — нет сетевого стека и прослушивания портов, меньше накладных расходов, встроенные ACL Windows, сохранение границ сообщений, работа через файловый интерфейс (`ReadFile`/`WriteFile`).

## 9. Что не проверено

- Обмен между двумя компьютерами (задание 6 в части «разные компьютеры») — проверен только сетевой формат имени на одной машине.
