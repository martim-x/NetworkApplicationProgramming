## 2. Архитектура (модель ConcurrentServer, глава 6)

```
                        ┌──────────────────────────────────────────┐
   RConsole ──pipe────► │ ConsolePipe  (команды start/stop/exit/…) │
                        └───────────────┬──────────────────────────┘
                                        │ общая область command[]
   клиент ──TCP────►  AcceptServer ─────┤ (неблокирующий listen, accept)
                            │           │
                            ▼           │
                     ListContact ───────┤  (критическая секция)
                            │           │
                  DispatchServer ───────┘  (событие «подключился клиент»)
                            │ читает код запроса: echo / time / rand
                            ▼
                 ServiceLibrary.dll: SSS → обслуживающий поток
                            │
                  GarbageCleaner (удаляет обслуженные элементы списка)
   клиент ──UDP────► ResponseServer  (ответ на широковещательный позывной)
```

Компоненты и их взаимодействие (таблица 7.9.1 практикума):

| Компонента | Назначение | Как реализована |
|---|---|---|
| `main` | главный поток: параметры, загрузка DLL, запуск и ожидание потоков | `LoadLibrary` + `GetProcAddress`, `CreateThread`, `WaitForSingleObject` |
| `AcceptServer` | подключение клиентов, обработка команд управления | неблокирующий `listen`-сокет (`ioctlsocket FIONBIO`), `accept`, `SleepEx(0, TRUE)` для APC |
| `DispatchServer` | диспетчеризация запросов | ожидание события, неблокирующий `recv` кода запроса, запуск обслуживающего потока через `SSS` |
| `GarbageCleaner` | сборка «мусора» | `Sleep(100)` + скан списка, закрытие сокета и дескриптора потока |
| `ConsolePipe` | серверная часть консоли управления | именованный канал `\\.\pipe\ConcurrentServer`, команды по протоколу `getcommand` |
| `ResponseServer` | поиск сервера в сети | UDP-сокет в неблокирующем режиме, ответ на позывной |
| `SSS` (DLL) | запуск обслуживающего потока | `CreateThread` + `SetThreadPriority(BELOW_NORMAL)` |
| `EchoServer` / `TimeServer` / `RandServer` | обслуживающие потоки | эхо, дата-время `dd.mm.yyyy/hh:mm:ss`, случайное 4-байтовое число |

Структуры данных (таблица 7.9.2):

| Структура | Состав | Назначение |
|---|---|---|
| `ListContact` | `socket`, `address`, `serviceThread`, `acceptThread`, `busy`, `finished`, `startedAt`, `messageCount`, `request` | одно подключение клиента и состояние его обслуживания |
| `TableService` | `code`, указатель на потоковую функцию | соответствие «код запроса → обслуживающий поток» |
| `StatsInfo` | `totalConnections`, `activeConnections`, `refusedConnections`, `completedConnections` | счётчики статистики (атомарные операции) |

## 3. Протокол

**Клиент → сервер (TCP):** первое сообщение — код запроса (`echo`, `time`, `rand`), далее — данные запроса.
- `echo`: сервер возвращает каждое принятое сообщение без изменения; сеанс завершается при закрытии клиентом или при сообщении нулевой длины;
- `time`: сразу после запроса сервер отправляет `дд.мм.гггг/чч:мм:сс`; продолжает отвечать, пока клиент шлёт `time`, и завершает сеанс при любой другой строке;
- `rand`: сервер отправляет 4 байта (int в формате Intel), продолжает по `rand`;
- неизвестный код: сервер отправляет `ErrorInquiry` и разрывает соединение (`отказ` в статистике).

**RConsole → сервер (именованный канал):** команда строкой, ответ — тот же код, если команда известна, иначе `nocmd`. Внутренняя служебная команда `getcommand` означает «сервер готов принять следующую команду».

**Поиск сервера (UDP):** клиент шлёт позывной на UDP-порт, `ResponseServer` отвечает этим же позывным.

## 4. Команды управления (таблица 7.9.3)

| Команда | Действие | Где обрабатывается |
|---|---|---|
| `start` | разрешить приём клиентов | `ProcessCommand` в `AcceptServer` |
| `stop` | запретить приём клиентов | там же |
| `statistics` | счётчики возвращаются в консоль по каналу (`total=… active=… completed=… refused=…`) и дублируются в журнал сервера | `ConsolePipe` (прямой ответ), плюс журнал |
| `wait` | приём запрещён, сервер дожидается обслуживания последних клиентов, команды обрабатываются и во время ожидания | там же (`drainMode`) |
| `shutdown` | `wait` + завершение работы сервера | там же |
| `exit` | немедленное завершение: активные сокеты закрываются, клиенты завершаются с ошибкой | там же (`InterruptActiveSessions`) |
| `getcommand` | служебная, ставится сервером после приёма команды | `ConsolePipe`/`TakeCommand` |
| `events` | служебная (только по каналу): возвращает очередь диагностики — подключение, завершение, отказ, таймаут — и очищает её | `ConsolePipe` |

## 5. Синхронизация и служебные механизмы (задания 18–21, 25, 29)

| Механизм | Где | Зачем |
|---|---|---|
| критическая секция `contactLock` | `AddContact`, `DispatchServer`, `GarbageCleaner` | одновременное добавление и удаление элементов `ListContact` разрушает список |
| критическая секция `commandLock` | `ConsolePipe`, `ProcessCommand` | общая область команды для нескольких потоков |
| событие `contactEvent` | `AcceptServer` → `DispatchServer` | сканировать список нужно только после очередного подключения |
| APC `QueueUserAPC` + `SleepEx(0, TRUE)` | обслуживающий поток → `AcceptServer` | асинхронные сообщения о старте и завершении обслуживания (задание 19) |
| `InterlockedIncrement/Exchange` | счётчики статистики, флаги | потоки работают асинхронно, обычный `++` теряет обновления (задание 25) |
| `SetThreadPriority` | `AcceptServer` (`ABOVE_NORMAL`), обслуживающие потоки (`BELOW_NORMAL`) | приём клиентов важнее обслуживания (задание 29) |

## 6. Трассировка вызовов Winsock2 и Win32

| Шаг | Сервер | Клиент |
|---|---|---|
| создание сокета | `socket(AF_INET, SOCK_STREAM, 0)` | `socket(AF_INET, SOCK_STREAM, 0)` |
| подготовка | `bind` + `listen` + `ioctlsocket(FIONBIO)` | `connect` |
| установка связи | `accept` (в цикле, неблокирующий) | — |

Что видно только на реальном прогоне: `DispatchServer` читает код запроса **до** запуска обслуживающего потока, поэтому `time` и `rand` отвечают сразу по коду запроса (иначе клиент ждал бы ответа, отправив запрос один раз). Счётчик сообщений включает сам код запроса — поэтому у `echo` с тремя сообщениями в журнале `сообщений 4`.

## 9. Правила динамических приоритетов (задание 30)

Реализовано первое правило из списка (по числу активных подключений). Остальные варианты можно добавить тем же механизмом:

- по числу активных подключений: пока `activeConnections` не выше порога — `NORMAL`, выше — `BELOW_NORMAL`, чтобы приём клиентов не голодал (**реализовано**);
- по времени обслуживания: если среднее время сеанса растёт, повышать приоритет `DispatchServer` и понижать обслуживающих;
- по типу запроса: `echo` (интерактивный) — выше, чем `rand`/`time` (короткие вычисления);
- периодический пересчёт в `GarbageCleaner` (раз в N секунд) через `SetThreadPriority` для потоков из `ListContact` (**реализовано**).

## 10. Сборка и запуск

```cmd
cl /nologo /EHsc /utf-8 /W3 /LD lab8\ServiceLibrary\ServiceLibrary.cpp /Fe:lab8\build\ServiceLibrary.dll
cl /nologo /EHsc /utf-8 /W3 lab8\ConcurrentServer\ConcurrentServer.cpp /Fe:lab8\build\ConcurrentServer.exe
cl /nologo /EHsc /utf-8 /W3 lab8\ClientTy\ClientTy.cpp /Fe:lab8\build\ClientTy.exe
```

Аргументы: `ConcurrentServer [TCP-порт] [DLL] [канал] [UDP-порт] [позывной] [лимит обслуживания мс]`, по умолчанию `2000 ServiceLibrary.dll \\.\pipe\ConcurrentServer 9200 ConcurrentServer 60000`.

Имя канала можно задавать коротким (`ConcurrentServer` → `\\.\pipe\ConcurrentServer`): сервер нормализует его так же, как клиенты ЛР6 и ЛР10, а сетевое имя отвергает — канал создаётся только локально.

Экспорт `SSS`/`FindService` ищется и в недекорированном виде, и в x86-декорированном (`_SSS@4`): `extern "C" __declspec(dllexport) ... WINAPI` на x64/ARM64 даёт имя без декорации, а в 32-битной сборке — с ней. Отсюда две типовые ошибки: «в библиотеке не найдены экспортируемые функции» (разрядность совпала, а имя искали недекорированное) и `LoadLibrary` с кодом 193 «не является допустимым приложением Win32» (DLL собрана под другую разрядность, чем EXE).

## 11. Вопросы для самопроверки

1. **Зачем `DispatchServer` работает с неблокирующим сокетом?** Иначе он мог бы зависнуть на `recv`, ожидая запрос от «молчащего» клиента, и остальные подключения ждали бы обслуживания (примечание к заданию 12).
2. **Почему обслуживающий поток переводит сокет в блокирующий режим?** Дальше с сокетом работает один поток, и блокирующие `recv`/`send` проще и дешевле, чем циклы опроса.
3. **Зачем нужна критическая секция вокруг `ListContact`?** `AcceptServer` добавляет элемент, `GarbageCleaner` удаляет; без синхронизации список разрушается (задание 18).
4. **Что даёт событие `contactEvent`?** `DispatchServer` не крутит холостой цикл, а просыпается после подключения клиента (задание 21).
5. **Как работает APC-уведомление?** Обслуживающий поток вызывает `QueueUserAPC` с дескриптором `AcceptServer`, а тот выполняет процедуру в `SleepEx(0, TRUE)`; так сообщения о старте и завершении печатаются в контексте `AcceptServer` (задание 19).
6. **Почему счётчики статистики атомарные?** Их меняют разные потоки; `InterlockedIncrement` исключает потерянные обновления (задание 25).
7. **Что происходит при неизвестном коде запроса?** `DispatchServer` отправляет `ErrorInquiry`, закрывает соединение, увеличивает счётчик отказов (задание 15).
8. **Зачем серверу DLL, а не встроенные функции?** Имя библиотеки — параметр `main`: можно подменить набор обслуживающих потоков без пересборки сервера (задание 14).
9. **Как сервер находит клиента в сети?** `ResponseServer` отвечает на широковещательный позывной, клиент получает адрес сервера (задание 28).
10. **Почему `getcommand` — служебная команда?** Она означает «команда принята и обработана»; по ней `ConsolePipe` понимает, что можно принимать следующую команду (таблица 7.9.3).
