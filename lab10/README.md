# Лабораторная работа №10: Удалённая консоль RConsole (ПР10)

Источник задания: практикум, раздел 7.11 «Разработка удаленной консоли», задания 1–2. Теория: главы 3, 5, 6; протокол канала — глава 4 (ЛР6).

## 1. Состав работы

| Задание практикума | Файл | Что реализовано |
|---|---|---|
| 1 — спецификация и API консоли | `ConsoleApi/ConsoleApi.h`, `ConsoleApi/ConsoleApi.cpp` | `ConnectConsole`, `SendConsoleCommand`, `IsKnownCommand`, `TrimCommand`, `PrintCommandHelp` |
| 2 — программа `RConsole` | `RConsole/RConsole.cpp` | ввод команд управления (таблица 7.9.3), вывод ответа сервера, сценарий и интерактивный режим |

## 2. Протокол взаимодействия консоли с сервером (задание 1)

Обмен идёт по именованному каналу (серверная сторона — поток `ConsolePipe` в ЛР8).

| Шаг | Консоль | Сервер |
|---|---|---|
| 1 | `CreateFile("\\.\pipe\<имя>")` | `ConnectNamedPipe` |
| 2 | `SetNamedPipeHandleState(PIPE_READMODE_MESSAGE)` | — |
| 3 | `WriteFile("<команда>")` | `ReadFile` → проверка команды |
| 4 | — | запись команды в общую область, ожидание `getcommand` |
| 5 | `ReadFile` → ответ | `WriteFile("<команда>")` или `WriteFile("nocmd")` |
| 6 | `CloseHandle` | `DisconnectNamedPipe`, ожидание следующего подключения |

Особенности реализации, вытекающие из устройства сервера:

- один экземпляр канала обслуживает **одну команду за подключение**, поэтому `SendConsoleCommand` подключается, отправляет команду, читает ответ и закрывает канал;
- если все экземпляры заняты, `CreateFile` возвращает `ERROR_PIPE_BUSY` (231); API ждёт через `WaitNamedPipe` и повторяет попытку;
- ответ сервера — подтверждение команды (тот же код) или `nocmd` для неизвестной команды;
- диагностические сообщения сервера (старт/завершение обслуживающих потоков, статистика) печатаются в консоли самого сервера; консоль получает подтверждение команды.

## 3. Команды управления (таблица 7.9.3)

| Команда | Действие на сервере |
|---|---|
| `start` | разрешить подключение клиентов |
| `stop` | запретить подключение клиентов |
| `statistics` | вернуть счётчики (`total=… active=… completed=… refused=…`) |
| `wait` | запретить приём и дождаться завершения обслуживания последнего клиента |
| `shutdown` | `wait`, затем завершение работы сервера |
| `exit` | завершение работы сервера; активные клиенты получают ошибку обмена |
| `help` | (только консоль) справка по командам |
| `quit` | (только консоль) выйти, не завершая сервер |

Неизвестная команда не отправляется на сервер: консоль сообщает об ошибке и подсказывает `help`.

События сервера (подключение клиента, завершение обслуживания, отказ, таймаут) показываются в RConsole: после каждой команды интерактивный и сценарный режим отправляют служебную команду `events` и печатают ответ построчно (`RConsole: событие: …`). Все операции канала ограничены таймаутом 5 с, при неудаче любой команды RConsole завершается с кодом 1.

## 4. Режимы работы

| Режим | Запуск | Поведение |
|---|---|---|
| сценарий | `RConsole.exe \\.\pipe\Имя statistics stop start` | выполняет команды по порядку, печатает ответы, останавливается на `exit`/`shutdown` |
| интерактивный | `RConsole.exe \\.\pipe\Имя` | приглашение `rconsole> `, команды вводятся построчно, `quit` — выход |
| проверка связи | любой запуск | при отсутствии сервера первая команда печатает операцию и код ошибки (`операция CreateFile, код 2` — канал не найден) |

## 5. Результаты локальной проверки (Windows 11, MSVC 14.51, localhost)

Сервер: `ConcurrentServer.exe 9301 ServiceLibrary.dll \\.\pipe\TestConsole 9300 TestServer`.

| Проверка | Ожидание | Факт |
|---|---|---|
| сценарий `statistics stop start statistics` | четыре подтверждения | `statistics -> statistics`, `stop -> stop`, `start -> start`, `statistics -> statistics` |
| неизвестная команда `reload` | отказ без отправки | `команда "reload" неизвестна` |
| интерактивный режим (`help`, `statistics`, `unknown-cmd`, `quit`) | справка, ответ сервера, ошибка, выход | вывод справки, `statistics -> statistics`, `команда "unknown-cmd" неизвестна`, `выход без завершения сервера` |
| консоль без сервера | понятная ошибка | `команда "statistics" не выполнена: операция CreateFile, код 2` |
| сервер-«молчун» (подключён, ответа нет) | таймаут за конечное время | `операция ReadFile, код 1460`, тест `build\test_consoleapi.exe` |
| сервер закрыл канал без ответа | точная причина | `операция ReadFile, код 109 (ERROR_BROKEN_PIPE)` |
| `shutdown` | сервер завершается сам | `shutdown -> shutdown`, процесс сервера завершился (`True`) |
| журнал сервера | все команды приняты | `ConsolePipe: принята команда "statistics" / "stop" / "start" / "shutdown"`, затем `сервер завершает работу (shutdown)` и финальная статистика |

Что выяснилось на прогоне: при первом подключении консоль получала `ERROR_PIPE_BUSY` — сервер ещё не завершил `DisconnectNamedPipe` предыдущего экземпляра. Лечится ожиданием `WaitNamedPipe` в `ConnectConsole` (реализовано). Второй нюанс: при передаче команд через конвейер PowerShell в первую строку попадал BOM (`\uFEFFhelp`), из-за чего команда считалась неизвестной; `TrimCommand` теперь срезает BOM.

Дополнительно (после аудита устойчивости): все операции консоли ограничены дедлайном 5 с — подключение, запись команды и чтение ответа делят общий таймаут; при таймауте чтение отменяется (`CancelIoEx`), поэтому сервер-«молчун» или занятый экземпляр не блокируют консоль навсегда. Результат возвращается структурой `ConsoleResult` (статус `CONSOLE_OK/CONNECT_FAILED/WRITE_FAILED/READ_FAILED/TIMEOUT`, payload, операция и точный код ошибки), а прежний `SendConsoleCommand` сохранён как обёртка для совместимости. Регресс-тесты: `ConsoleApi\tests\test_consoleapi.cpp`, сборка — `cl /nologo /EHsc /utf-8 /W3 ConsoleApi\tests\test_consoleapi.cpp /Fe:build\test_consoleapi.exe`, запуск — `build\test_consoleapi.exe` (7 тестов). Пробного подключения при старте больше нет: первая же команда сама устанавливает соединение.

Имя канала можно передавать коротким (`TestConsole` → `\\.\pipe\TestConsole`): `NormalizePipeName` в `ConsoleApi` достраивает префикс, поэтому разные формы имени у сервера и консоли больше не дают код 2 «не удаётся найти указанный файл».

## 7. Вопросы для самопроверки

1. **Почему консоль подключается заново на каждую команду?** `ConsolePipe` в сервере обслуживает по одной команде на экземпляр канала и после ответа вызывает `DisconnectNamedPipe` (ЛР6, ЛР8); протокол «одна команда — одно подключение» проще и не требует держать состояние сеанса.
2. **Что делать при `ERROR_PIPE_BUSY`?** Подождать освобождения экземпляра `WaitNamedPipe` и повторить `CreateFile`; иначе команда теряется (именно эта ошибка была получена при первом прогоне).
3. **Почему нужен `SetNamedPipeHandleState(PIPE_READMODE_MESSAGE)`?** Иначе `ReadFile` вернёт поток байт без границ сообщений, и ответ сервера нельзя надёжно отделить от следующего.
4. **Что означает ответ `nocmd`?** Сервер получил неизвестную команду; консоль должна показать справку.
5. **Как консоль узнаёт, что сервер завершился?** После `exit`/`shutdown` сервер отвечает подтверждением и закрывает канал; следующая попытка подключения вернёт `ERROR_FILE_NOT_FOUND`.
6. **Зачем был нужен `FlushFileBuffers` на клиенте?** В прежней версии — да: запись в канал в режиме сообщений должна быть доставлена до чтения ответа. Сейчас сброс убран: `FlushFileBuffers` заставлял клиента ждать, пока сервер прочитает сообщение, и «молчащий» сервер подвешивал консоль до бесконечности; в режиме сообщений сообщение и так доступно серверному `ReadFile`.
7. **Почему команды `start`/`stop` обрабатывает `AcceptServer`, а не `ConsolePipe`?** `ConsolePipe` только принимает команду и кладёт её в общую область; поток-получатель (`AcceptServer`) меняет состояние приёма клиентов — так разделены транспорт и логика (задание 22 практикума ПР8).
8. **Чем `shutdown` отличается от `exit`?** `shutdown` сначала ждёт завершения обслуживания активных клиентов, затем завершает сервер; `exit` завершает сразу.

## 8. Что не проверено

- Работа консоли с другого компьютера (проверка на одной машине, локальный канал).
- Потоковая передача событий в реальном времени: события приходят по запросу (`events` после каждой команды), а не push-уведомлением.
