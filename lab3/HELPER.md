## 1. Что такое сокет, ориентированный на сообщения (SOCK_DGRAM)?

**Сокет, ориентированный на сообщения (SOCK_DGRAM)** — сокет, использующий протокол **UDP** (User Datagram Protocol). В Winsock2 создаётся вызовом `socket(AF_INET, SOCK_DGRAM, 0)`.

Ключевые свойства (лекция 3.4, рис. 3.4.1):
- Обмен данными происходит **пакетами (дейтаграммами)** протокола UDP.
- **Нет установления соединения** — нет `listen`/`accept` на сервере и нет `connect` на клиенте.
- **Не гарантирует доставку** — дейтаграмма может быть потеряна, продублирована или прийти в ином порядке.
- **Не гарантирует порядок** — порядок получения может не совпадать с порядком отправки.
- Контроль за доставкой и порядком сообщений **возлагается на само приложение**.
- Применяется для пересылки **коротких** и/или **широковещательных** сообщений.

В коде ServerU/ClientU (lab3):
```cpp
// ServerU.cpp:64, ClientU.cpp:76
if ((sS = socket(AF_INET, SOCK_DGRAM, 0)) == INVALID_SOCKET)
```

## 2. В чём принципиальное различие схем взаимодействия с установлением соединения (TCP) и без установления соединения (UDP)?

| Характеристика | TCP (SOCK_STREAM) | UDP (SOCK_DGRAM) |
|---|---|---|
| **Установление соединения** | Требуется (`listen` → `accept` / `connect`) | Не требуется |
| **Функции обмена** | `send` / `recv` (по установленному каналу) | `sendto` / `recvfrom` (адресат в каждом вызове) |
| **Надёжность** | Гарантирована (последовательность, подтверждения, повторные передачи) | Не гарантируется |
| **Порядок доставки** | Строго соответствует порядку отправки | Может нарушаться |
| **Границы сообщений** | Поток байт — границ нет | Сохраняются (одна дейтаграмма = одно сообщение) |
| **Нагрузка на приложение** | Минимальная (TCP берёт на себя надёжность) | Приложение само обеспечивает подтверждения/повторы при необходимости |
| **Типичное применение** | Файлы, веб, почта, длинные сессии | DNS, DHCP, VoIP, игры, broadcast, короткие запросы |

(Лекция 3.4, рис. 3.4.1 и 3.4.2; практикум задания 1–8)

В коде:
- **ServerT (лаба 2)**: `listen` → `accept` → `send`/`recv` по возвращённому сокету.
- **ServerU (лаба 3)**: `bind` → сразу `recvfrom`/`sendto` с адресом клиента.
- **ClientT (лаба 2)**: `connect` → `send`/`recv`.
- **ClientU (лаба 3)**: нет `connect`, сразу `sendto`/`recvfrom` с адресом сервера.

## 3. Какие функции Winsock2 используются для обмена данными в режиме без соединения (UDP)?

**`sendto`** — отправка сообщения без установления соединения.  
**`recvfrom`** — приём сообщения без установления соединения.

Прототипы (лекция 3.2, табл. 3.2.1; 3.12–3.13):

```cpp
int sendto(
    SOCKET s,                 // [in] дескриптор сокета
    const char* buf,          // [in] буфер данных
    int len,                  // [in] размер буфера
    int flags,                // [in] индикатор режима (обычно 0)
    const struct sockaddr* to,// [in] указатель на SOCKADDR_IN получателя
    int tolen                 // [in] длина структуры to
);

int recvfrom(
    SOCKET s,                 // [in] дескриптор сокета
    char* buf,                // [out] буфер для приёма
    int len,                  // [in] размер буфера
    int flags,                // [in] индикатор режима (обычно 0)
    struct sockaddr* from,    // [out] сюда запишутся параметры отправителя
    int* fromlen              // [in/out] указатель на размер from
);
```

**Важные нюансы (из кода лабы 3, отступления от пособия):**
- `recvfrom` **не записывает нуль-терминатор** в буфер. В пособии и helper-коде используется `sizeof(buf)`, что приводит к чтению мусора за границей принятых данных.
  - **Правильно (ServerU.cpp:95, ClientU.cpp:110):**
    ```cpp
    lb = recvfrom(sS, ibuf, sizeof(ibuf) - 1, 0, ...);
    ibuf[lb] = '\0'; // явное завершение строки
    ```
- `sendto` в UDP **всегда требует адрес получателя** (`to`, `tolen`) — даже если клиент «знает» сервер, адрес передаётся при каждом вызове.
- В `sendto` длина буфера — `strlen(buf) + 1` (с терминатором), чтобы получатель корректно напечатал строку.

## 4. Как сервер UDP узнаёт адрес клиента для ответа?

При вызове `recvfrom` структура `SOCKADDR_IN` (переданная по указателю в параметре `from`) **автоматически заполняется** параметрами сокета **отправителя** (IP-адрес и порт). Этот же адрес затем передаётся в `sendto` для ответа.

Код ServerU.cpp (строки 82–83, 95, 113):
```cpp
SOCKADDR_IN clientAddress;
int clientAddressSize = sizeof(clientAddress);

lb = recvfrom(sS, ibuf, sizeof(ibuf) - 1, 0,
              (sockaddr*)&clientAddress, &clientAddressSize);
// ...
sendto(sS, ibuf, lb, 0, (sockaddr*)&clientAddress, clientAddressSize);
```

Это ключевое отличие от TCP: в TCP адрес клиента известен после `accept` и дальше используется неявно (через соединённый сокет), а в UDP **адрес нужно явно передавать при каждом `sendto`**.

## 5. Зачем в UDP-клиенте не нужен `bind`?

В TCP клиент обычно не вызывает `bind` — ОС сама выделяет **эфемерный порт** (диапазон 49152–65535) при вызове `connect`.  
В UDP то же самое: при создании сокета `socket(AF_INET, SOCK_DGRAM, 0)` Windows автоматически назначает сокету свободный эфемерный порт. Клиент не нуждается в *фиксированном* порту — сервер узнает порт клиента из `recvfrom` и отвечает туда.

Код ClientU.cpp (строки 74–77):
```cpp
// bind не нужен — Windows выделяет клиенту эфемерный порт
if ((cC = socket(AF_INET, SOCK_DGRAM, 0)) == INVALID_SOCKET)
    throw SetErrorMsgText("socket:", WSAGetLastError());
```

**Когда `bind` может понадобиться клиенту UDP:** если клиент должен принимать данные на *известном заранее* порте (например, для_symметричного_ обмена или если за NAT нужен фиксированный порт для hole punching). В лабе 3 это не требуется.

## 6. Как выглядит структура взаимодействия клиент-сервер в UDP (по лекции 3.4, рис. 3.4.1)?

Пять блоков в каждой программе:

| Блок | Сервер (ServerU) | Клиент (ClientU) |
|---|---|---|
| **1** | `WSAStartup` — инициализация WS2_32.DLL | `WSAStartup` — то же самое |
| **2** | `socket(SOCK_DGRAM)` → `bind` (фиксированный порт, напр. 2000) | `socket(SOCK_DGRAM)` — **нет `bind`**, ОС даёт эфемерный порт |
| **3** | `recvfrom` — **блокируется**, ждёт дейтаграмму от клиента. При приёме заполняет `clientAddress` | `sendto` — шлёт дейтаграмму на известные IP/порт сервера |
| **4** | `sendto` — отвечает клиенту, используя адрес из `recvfrom` | `recvfrom` — принимает ответ (адрес сервера уже известен) |
| **5** | `closesocket` → `WSACleanup` | `closesocket` → `WSACleanup` |

**Синхронизация:** нет явной (в отличие от TCP `listen`/`accept`/`connect`). Сервер просто ждёт на `recvfrom`, клиент шлёт `sendto` — первая дейтаграмма и есть «запрос».

## 7. Как организовать обмен несколькими сообщениями в UDP (задание 7 лабы 3)?

Поскольку UDP не имеет соединения, «сессию» моделирует приложение:
1. Клиент спрашивает у пользователя **число сообщений** (`messageTotal`).
2. В цикле `for (i = 1; i <= messageTotal; i++)`:
   - Клиент: `sendto` → `recvfrom` (эхо от сервера).
   - Сервер: `recvfrom` → `sendto` (эхо обратно).
3. После цикла клиент шлёт **нулевое сообщение** (дейтаграмма из одного байта `'\0'`) — сигнал «конец обмена».
4. Сервер при получении `ibuf[0] == '\0'` выходит из внутреннего цикла, печатает статистику и ждёт следующего клиента (внешний `while(true)`).

Код ClientU.cpp (строки 86–132):
```cpp
cout << "Enter number of messages: ";
cin >> messageTotal;

receivedCount = 0;
startTime = clock();
for (int i = 1; i <= messageTotal; i++) {
    sprintf(sendBuffer, "Hello from ClientU %03d", i);
    sendto(cC, sendBuffer, (int)(strlen(sendBuffer) + 1), 0, ...);
    lb = recvfrom(cC, receiveBuffer, sizeof(receiveBuffer) - 1, 0, ...);
    receiveBuffer[lb] = '\0';
    receivedCount++;
    cout << "Received: " << receiveBuffer << endl;
}
endTime = clock();
// нулевое сообщение — конец обмена
sendto(cC, "", 1, 0, ...);
```

Код ServerU.cpp (строки 80–124):
```cpp
map<string, int> messageCounts; // счётчики сообщений: ключ — IP клиента (строка), значение — число его сообщений

while (true) { // внешний цикл — ожидание следующего клиента
    startTime = clock();
    while (true) { // внутренний цикл — обмен с текущим клиентом
        lb = recvfrom(sS, ibuf, sizeof(ibuf) - 1, 0, ...);
        ibuf[lb] = '\0';
        if (ibuf[0] == '\0') break; // конец обмена с этим клиентом
        messageCounts[inet_ntoa(clientAddress.sin_addr)]++; // счётчик по IP-адресу отправителя
        cout << "From " << inet_ntoa(clientAddress.sin_addr) << ":" << ntohs(clientAddress.sin_port) << ": " << ibuf << endl;
        sendto(sS, ibuf, lb, 0, (sockaddr*)&clientAddress, clientAddressSize);
    }
    endTime = clock();
    // статистика: messageCounts[IP] завершившегося клиента, затем messageCounts.erase(IP)
}
```

## 8. Как оценить скорость передачи и потери в UDP (задания 7–8 лабы 3)?

- **Время обмена**: замеряется через `clock()` до и после цикла обмена. Разница в тактах / `CLOCKS_PER_SEC` = секунды.
- **Число отправленных**: `messageTotal` (ввод пользователя).
- **Число полученных**: `receivedCount` (клиент); на сервере — карта `map<string, int> messageCounts`, ключ — IP-адрес клиента (строка), значение — число принятых от него сообщений.
- **Потери**: если `receivedCount < messageTotal` — есть потери дейтаграмм (характерно для UDP при нагрузке/буферных переполнениях).

Код ClientU.cpp (строки 121–127):
```cpp
cout << "\nExchange time for " << messageTotal << " messages: "
     << ((double)(endTime - startTime)) / CLOCKS_PER_SEC << " seconds.\n";
cout << "Sent: " << messageTotal << ", received: " << receivedCount << endl;
```

Сравнение с лабой 2 (TCP): при одинаковом числе сообщений TCP покажет **нет потерь** и обычно **большее время** (накладные расходы на установление соединения, подтверждения, управление потоком), UDP — возможны потери, но меньше оверхед на сообщение.

## 9. Что такое интерфейс внутренней петли (loopback) и зачем он нужен в лабе 3?

**Интерфейс внутренней петли (loopback interface)** позволяет двум процессам на **одном хосте** обмениваться данными через стек TCP/IP, **не выходя во внешнюю сеть**. Дейтаграммы формируются нормально, но не покидают хост.

- Зарезервирована сеть `127.0.0.0/8`.
- Стандартный адрес: **`127.0.0.1`**, имя: **`localhost`**.
- В лабе 3: по умолчанию клиент подключается к `127.0.0.1:2000` (ClientU.cpp:55–56), сервер биндится на `INADDR_ANY` (ServerU.cpp:71), что включает loopback.

Применение: **отладка распределённых приложений на одном компьютере** — моделирование сети без физической сети (лекция 3.4, описание рис. 3.4.1; вопрос 29 лабы 2).

string GetErrorMsgText(int code) {
    switch (code) {
        case WSAEINTR: return "WSAEINTR: Работа функции прервана";

    return msgText + GetErrorMsgText(code);
}

## 13. Контрольные вопросы к защите (из практикума Глава 7)

1. **Какие функции используются для обмена данными без установки соединения?**  
   → `sendto` / `recvfrom` (вопрос 3).

2. **В чём отличие `sendto` от `send`?**  
   → `sendto` требует адрес получателя (`to`, `tolen`), работает только с `SOCK_DGRAM`; `send` — по установленному каналу (TCP), адрес не нужен.

3. **Зачем серверу UDP `bind`, а клиенту — нет?**  
   → Серверу нужен **фиксированный известный порт**, чтобы клиенты могли ему писать. Клиенту порт выделит ОС (эфемерный), сервер узнает его из `recvfrom`.

4. **Как сервер узнаёт адрес клиента в UDP?**  
   → Из параметра `from` функции `recvfrom` — она заполняет `SOCKADDR_IN` отправителя.

5. **Почему `recvfrom` не ставит `\0` в конец буфера?**  
   → UDP передаёт **бинарные данные**, не только строки. Функция возвращает длину (`lb`), приложение само решает, как интерпретировать байты.

6. **Что такое эфемерный порт и в каком диапазоне он выделяется?**  
   → Временный порт, выделяемый ОС клиенту при создании сокета без `bind`. Диапазон **49152–65535** (IANA Dynamic Ports).

7. **Какие гарантии даёт UDP?**  
   → **Никаких**: нет гарантии доставки, порядка, защиты от дублей. Только контрольная сумма (опциональная в IPv4, обязательная в IPv6).

8. **Как обнаружить потерю дейтаграмм в приложении?**  
   → Нумерация сообщений (sequence number) + таймауты + повторная передача (прикладной протокол над UDP). В лабе 3: счётчик `receivedCount` vs `messageTotal`.

9. **Зачем нулевое сообщение (`\0`) в конце обмена?**  
   → Прикладной маркер «конец сессии», так как UDP не имеет FIN/ACK как TCP.

10. **Что такое loopback и зачем он в лабе?**  
    → Адрес `127.0.0.1`, позволяет тестировать клиент-сервер на одной машине без сети.

|---|---|
| «Почему у вас `sizeof(buf) - 1` в `recvfrom`?» | Чтобы оставить 1 байт под `\0`, который `recvfrom` не пишет. Без этого `cout << buf` выведет мусор. |
| «А если дейтаграмма больше 50 байт?» | `recvfrom` обрежет до `len` (50), остаток потерян (UDP — сообщения не фрагментируются приёмником). В лабе сообщения короткие (`"Hello from ClientU 001"` < 50). |
| «Почему сервер в внешнем `while(true)`?» | Итеративный UDP-сервер: после завершения обмена с одним клиентом (нулевое сообщение) возвращается к `recvfrom` и ждёт следующего. |
| «Может ли UDP-сервер обслуживать нескольких клиентов одновременно?» | В данном коде — **нет**, итеративный (последовательно). Для параллельного — нужен `select`/`poll`/`IOCP` или поток на клиента (как в лабе 6). |
| «Что вернёт `recvfrom` при ошибке?» | `SOCKET_ERROR` (-1), код ошибки — `WSAGetLastError()` (напр. `WSAECONNRESET` если ICMP Port Unreachable). |
| «Зачем `htons`/`ntohs`?» | Порядок байт в сети — **big-endian**, на x86 — **little-endian**. `htons` конвертирует порт в сетевой порядок перед записью в `sin_port`. |
