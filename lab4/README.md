## 2. Теория: зачем нужен широковещательный адрес

Клиент не знает сетевой адрес сервера, но знает **номер порта** и **позывной** (набор символов, например `Hello`). Запрос отправляется на широковещательный адрес — его получают все узлы сегмента, а отвечает только тот, у кого позывной совпал. Приложение перестаёт зависеть от конкретного адреса сервера (раздел 3.15: «распределенное приложение не должно быть привязано к конкретным параметрам сокетов»).

| Адрес | Что адресует | Пример из прогона |
|---|---|---|
| ограниченное широковещание `INADDR_BROADCAST` (255.255.255.255) | все узлы локального сегмента; маршрутизаторами не передаётся | `ClientB Hello 9101 255.255.255.255` |
| направленное широковещание подсети: `IP & маска \| ~маска` | только узлы конкретной подсети | при 172.20.10.4/28 → `172.20.10.15` |
| широковещание интерфейса петли | только локальный стек | `127.255.255.255` |
| `INADDR_ANY` (0.0.0.0) в `bind` | приём на всех интерфейсах; это **не** адрес назначения | `bind(... INADDR_ANY ...)` в `GetRequestFromClient` |

Раздел 3.15 прямо задаёт три правила:

- широковещание возможно **только в UDP** (`SOCK_DGRAM`, `sendto`/`recvfrom`): TCP требует установленного соединения с одним конкретным адресом, а широковещательный адрес не может быть стороной соединения;
- адрес `INADDR_BROADCAST` по умолчанию запрещён — нужен `setsockopt(..., SOL_SOCKET, SO_BROADCAST, ...)`, иначе `sendto` вернёт `SOCKET_ERROR` с `WSAEACCES`;
- широковещательные пакеты не проходят через маршрутизаторы и шлюзы, поэтому метод работает **только внутри сегмента локальной сети**.

Сверх пособия (проверено фактически, см. раздел 5): направленное широковещание подсети и широковещание петли локальный стек тоже принимает, если сервер уже привязал сокет. В IPv6 широковещания нет вовсе — там используется multicast; это ограничение IPv4, а не Winsock.

## 3. Протокол обмена

```
Клиент                                          Сервер
socket(SOCK_DGRAM)                              socket(SOCK_DGRAM)
setsockopt(SO_BROADCAST)                        setsockopt(SO_REUSEADDR)
setsockopt(SO_RCVTIMEO, 3000)                   bind(INADDR_ANY : порт)
sendto("Hello") ------- broadcast -------------> recvfrom → "Hello"? да
                                                sendto("Hello", адрес клиента)
recvfrom <---------------- отклик --------------
strcmp(отклик, "Hello") == 0 → сервер найден
```

Позывной работает и как запрос, и как подтверждение: обе стороны сравнивают строку `strcmp`, поэтому чужой позывной отбрасывается. Проверка идёт по **содержимому**, а не по адресу отправителя — поэтому ответ приходит с другого порта (см. раздел 5, наблюдение 2).

## 4. Разбор по заданиям

**Задание 1.** `GetRequestFromClient(name, port, from, flen)` создаёт UDP-сокет, ставит `SO_RCVTIMEO` (3000 мс) и `SO_REUSEADDR`, привязывается к `INADDR_ANY:port`, переводит сокет в неблокирующий режим (`ioctlsocket(FIONBIO)`) и читает датаграммы в цикле до 3 с. Совпало с `name` — заполняет `from`/`flen`, закрывает сокет и возвращает `true`; пришло чужое — печатает `отклонён чужой запрос: "<строка>"` и продолжает ждать; вышло время — `false`; любая другая ошибка — `throw`. `SO_REUSEADDR` здесь не украшение: без него второй сервер с тем же позывным на том же порту не привязался бы (`WSAEADDRINUSE`), а задание 6 требует именно двух таких серверов.

**Задание 2.** `PutAnswerToClient(name, to, lto)` создаёт отдельный сокет, переводит его в неблокирующий режим и отправляет позывной по адресу клиента из `recvfrom`; при `WSAEWOULDBLOCK` повторяет `sendto` (до 50 попыток с `Sleep(10)`). Порт ответа не 9101, а эфемерный — сокет не привязан, номер назначает ОС.

**Задание 3.** `main` сервера крутит бесконечный цикл «ожидание → ответ»; после таймаута печатает `запросов нет (таймаут ожидания)` и ждёт снова, поэтому обслуживаются любые клиенты по очереди.

**Задание 4.** `GetServer(call, port, from, flen, broadcastAddress)` разрешает `SO_BROADCAST`, ставит `SO_RCVTIMEO` 3000 мс, отправляет позывной по широковещательному адресу и ждёт отклик. Позывной совпал — `true` и параметры сокета сервера в `from`; таймаут — `false`; чужой отклик — обнуляет `from` и возвращает `false`.

**Задание 5.** Клиент печатает `IP:порт` откликнувшегося сервера, сервер — `IP:порт` клиента, отправившего правильный позывной.

**Задание 6.** `CountServers(call, port, broadcastAddress)` вызывается при старте сервера **до** привязки своего сокета: широковещательный запрос, сбор всех откликов с подсчётом уникальных адресов (`set<string>`), затем предупреждение, если найден хотя бы один другой сервер с тем же позывным.

**Адрес по умолчанию.** Если третий аргумент не задан, программа сама вычисляет направленный широковещательный адрес активного адаптера: `GetAdaptersInfo` → `ip & mask | ~mask`. На машине прогона получилось `172.20.10.15` (адрес `172.20.10.4`, маска `255.255.255.240`, то есть /28).

**Неблокирующий режим (задание 27 практикума ПР8).** Изначально `GetRequestFromClient` ждал датаграмму блокирующим `recvfrom` с `SO_RCVTIMEO` — поток на это время остановлен (примечание к 7.5.5). Теперь оба сокета переводятся в режим без блокировки, приём идёт циклом с `Sleep(10)` до истечения 3 с, а `PutAnswerToClient` повторяет `sendto` при `WSAEWOULDBLOCK`. Поведение снаружи не изменилось — прогон ниже это подтверждает.

| 8 | второй `ServerB Hello 9101` рядом с первым | предупреждение о найденном сервере | `отклик от 172.20.10.4:64197` → `ВНИМАНИЕ: в сети обнаружены серверы с позывным "Hello": 1` |

Наблюдения, которые стоит держать в голове на защите:

1. **Все три вида широковещательных адресов доставляются локальному стеку** — но только если сервер уже привязал сокет. Между стартом сервера и `bind` есть окно (опрос сети в `CountServers`, ~0.7 с по `SO_RCVTIMEO`), поэтому клиент, запущенный сразу после сервера, может не получить отклик.
2. **Ответ приходит с эфемерного порта**: `PutAnswerToClient` создаёт новый сокет без `bind`, ОС назначает ему случайный номер (64182, 64185…). Клиент это не проверяет — сверяется только позывной, поэтому обмен работает. Если бы клиент требовал ответ именно с порта 9101, протокол сломался бы.
3. **Два сервера на одном порту работают**: `SO_REUSEADDR` позволяет обоим привязаться, широковещательная датаграмма доходит до обоих (в логе оба печатают `Запрос от клиента …:64198`), отвечают тоже оба, а клиент делает **один** `recvfrom` и берёт первый отклик. Остальные отклики остаются в буфере сокета и теряются при закрытии.
4. **Таймаут клиента — 3 с** (`SO_RCVTIMEO` 3000): сценарий 6 занял 3.07 с, то есть ожидание действительно ограничено, а не бесконечно.

|---|---|---|---|

## 8. Вопросы для самопроверки (с ответами)

1. **Почему широковещание возможно только в UDP?** TCP — протокол с установленным соединением: `connect` фиксирует адрес одного узла, а широковещательный адрес не может быть стороной соединения (3.15). Плюс TCP подтверждает доставку и порядок, а широковещательная датаграмма адресована всем сразу.
2. **Зачем `SO_BROADCAST`?** По умолчанию отправка на широковещательный адрес запрещена; опция снимает запрет. Без неё `sendto` вернёт `SOCKET_ERROR` с `WSAEACCES`.
3. **Чем ограниченное широковещание отличается от направленного?** `255.255.255.255` адресует все узлы каждого локального сегмента (и никогда не пересылается маршрутизатором); направленный `172.20.10.15` — только узлы конкретной подсети `172.20.10.0/28`.
4. **Почему на одной машине работают все три адреса?** Локальный стек принимает и ограниченное широковещание, и направленное широковещание своей подсети, и широковещание петли `127.255.255.255`. Проверено фактически — сценарии 2–4.
5. **Почему приёмник привязывается к `INADDR_ANY`, а не к широковещательному адресу?** `bind` задаёт **локальный** адрес сокета, а не адрес назначения. `INADDR_ANY` означает «все локальные интерфейсы», поэтому датаграмма, пришедшая на широковещательный адрес или на адрес адаптера, будет принята.
6. **Что будет, если позывной не совпал?** Сервер игнорирует датаграмму и продолжает ждать (сценарии 5, 7); клиент при чужом отклике обнуляет структуру адреса и возвращает `false`.
7. **Зачем серверу `SO_REUSEADDR`?** Чтобы два сервера с одним позывным могли привязаться к одному порту — этого требует задание 6. Без опции второй `bind` упадёт с `WSAEADDRINUSE`.
8. **Почему ответ сервера приходит не с порта 9101?** `PutAnswerToClient` создаёт новый сокет и не вызывает `bind`, поэтому ОС назначает эфемерный порт (в прогоне 64182–64199). Протокол это допускает: клиент проверяет позывной, а не адрес отправителя.
9. **Как обработать несколько откликов серверов?** Читать `recvfrom` в цикле до таймаута и собирать адреса в множество — так сделано в `CountServers`. Клиент `GetServer` делает один `recvfrom` и берёт первый отклик — это ограничение текущей реализации, а не алгоритма.
10. **Что ограничивает область применения метода?** Маршрутизаторы и шлюзы не пропускают широковещательные пакеты, поэтому метод работает только внутри сегмента локальной сети; для выхода за его пределы нужен либо известный адрес, либо разрешение имён (ПР5), либо многоадресная рассылка.
11. **Почему позывной сравнивают через `strcmp`, а не по длине?** Сравнение по содержимому отбрасывает и чужие позывные, и «похожие» строки; длина совпадёт у любых двух строк одинакового размера, поэтому критерием быть не может.
12. **Что изменится, если сервер запустить после клиента?** Клиент отправит запрос в пустоту и завершится по таймауту 3 с (`Сервер с позывным "Hello" не найден`): широковещательные датаграммы не буферизуются для будущих получателей.
