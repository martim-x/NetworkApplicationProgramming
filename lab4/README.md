## 2. Теория: зачем широковещательный адрес

Клиент не знает IP-адрес сервера, но знает номер порта и позывной (набор символов, например `Hello`). Тогда запрос отправляется на широковещательный адрес — его получают все узлы сегмента сети, а отвечает только тот, чей позывной совпал. Так распределённое приложение перестаёт зависеть от конкретного адреса сервера.

| Адрес | Что адресует | Пример |
|---|---|---|
| ограниченное широковещание `INADDR_BROADCAST` (255.255.255.255) | все узлы локального сегмента, маршрутизаторами не передаётся | `255.255.255.255` |
| направленное широковещание подсети | все узлы конкретной подсети: `IP & маска \| ~маска` | при адресе 192.168.31.80/24 → `192.168.31.255` |
| широковещание интерфейса петли | только локальный стек | `127.255.255.255` |
| `INADDR_ANY` (0.0.0.0) при `bind` | приём на всех интерфейсах, это не адрес назначения | `bind(... INADDR_ANY ...)` |

Ключевые правила из раздела 3.15:

- широковещание возможно **только в UDP** (`SOCK_DGRAM`, `sendto`/`recvfrom`); TCP требует уже установленного соединения с конкретным адресом;
- отправка на широковещательный адрес требует разрешения `setsockopt(..., SOL_SOCKET, SO_BROADCAST, ...)`, иначе `sendto` завершается ошибкой `WSAEACCES`;
- широковещательные пакеты не проходят через маршрутизаторы, поэтому метод работает только внутри сегмента локальной сети;
- в сети может оказаться несколько серверов с одним позывным — клиент должен уметь обработать несколько откликов и выбрать сервер (первый подходящий);
- блокирующий `recvfrom` в функциях поиска — известный недостаток (`примечание` к разделу 7.5.5 практикума), который исправляется неблокирующим режимом в ПР8/ПР9.

## 3. Протокол обмена

```
Клиент                                        Сервер
socket(SOCK_DGRAM)
setsockopt(SO_BROADCAST)
setsockopt(SO_RCVTIMEO)
sendto("Hello") ---------------broadcast-----> bind(INADDR_ANY:порт)
                                              recvfrom → "Hello"? да
recvfrom <---------------- ответ ------------- sendto("Hello", адрес клиента)
сравнение отклика с позывным
```

Позывной используется и как запрос, и как подтверждение: и сервер, и клиент проверяют точное совпадение строки (`strcmp`), поэтому чужой позывной отбрасывается.

## 4. Разбор по заданиям

**Задание 1.** `GetRequestFromClient(name, port, from, flen)` создаёт UDP-сокет, ставит `SO_RCVTIMEO` (3000 мс) и `SO_REUSEADDR`, привязывается к `INADDR_ANY:port` и читает датаграммы в цикле. Совпало с `name` — заполняет `from`/`flen` и возвращает `true`; пришло чужое — печатает «отклонён чужой запрос» и продолжает ждать; истёк таймаут (`WSAETIMEDOUT`) — возвращает `false`; любая другая ошибка — `throw` через `SetErrorMsgText`.

**Задание 2.** `PutAnswerToClient(name, to, lto)` создаёт отдельный сокет и отправляет позывной по адресу клиента из `recvfrom`.

**Задание 3.** `main` сервера крутит бесконечный цикл «ожидание → ответ», поэтому обслуживаются любые клиенты по очереди.

**Задание 4.** `GetServer(call, port, from, flen, broadcastAddress)` разрешает `SO_BROADCAST`, отправляет позывной по широковещательному адресу, ждёт отклик; совпал — `true` и параметры сокета сервера в `from`; таймаут или чужой отклик — `false`.

**Задание 5.** Клиент печатает `IP:порт` откликнувшегося сервера, сервер печатает `IP:порт` клиента, отправившего правильный позывной.

**Задание 6.** `CountServers(call, port, broadcastAddress)` вызывается при старте сервера: широковещательный запрос до привязки своего сокета, сбор всех откликов с подсчётом уникальных адресов (`set<string>`), затем предупреждение в консоль, если найден хотя бы один другой сервер с тем же позывным.

**Адрес по умолчанию.** Если четвёртый аргумент не задан, программа сама вычисляет направленный широковещательный адрес активного адаптера: `GetAdaptersInfo` → `ip & mask | ~mask` (в проверке на этой машине получилось `192.168.31.255`).

**Неблокирующий режим (задание 27 практикума ПР8).** Изначально `GetRequestFromClient` ждал датаграмму блокирующим `recvfrom` с `SO_RCVTIMEO` — поток на это время остановлен. Теперь оба сокета переводятся в режим без блокировки (`ioctlsocket(..., FIONBIO, ...)`), приём идёт циклом с `Sleep(10)` до истечения 3 с, а `PutAnswerToClient` повторяет `sendto` при `WSAEWOULDBLOCK`. Поведение снаружи не изменилось: те же три широковещательных адреса, тот же отказ на чужой позывной (проверено повторно).

## 5. Результаты локальной проверки (Windows 11, MSVC 14.51, одна машина, внутренняя петля и локальный сегмент)

| Проверка | Ожидание | Факт |
|---|---|---|
| `ClientB Hello 9101` без адреса (автоопределение) | сервер найден по `192.168.31.255` | `Сервер найден: 192.168.31.80:64600` |
| адрес `255.255.255.255` | сервер найден | `Сервер найден: 192.168.31.80:64602` |
| адрес `127.255.255.255` (петля) | сервер найден | `Сервер найден: 127.0.0.1:64604` |
| адрес `192.168.31.255` | сервер найден | `Сервер найден: 192.168.31.80:64606` |
| позывной `Other` | отказ | `Сервер с позывным "Other" не найден`, сервер: `отклонён чужой запрос: "Other"` |
| порт 9102 (никого нет) | отказ | `Сервер с позывным "Hello" не найден` |
| второй `ServerB Hello 9101` рядом с первым | предупреждение о найденном сервере | `ВНИМАНИЕ: в сети обнаружены серверы с позывным "Hello": 1` |

Что выяснилось фактически: все три широковещательных адреса доставляются локальному стеку, но только если сервер уже привязал сокет. Между стартом сервера и привязкой есть окно (опрос сети в `CountServers` ~0.7 с), поэтому клиент, отправленный сразу после запуска сервера, может не получить отклик. Это же окно — следствие того, что `GetRequestFromClient` создаёт сокет заново на каждый вызов; в ПР8 (задание 27) недостаток устраняется неблокирующим режимом.

| | lab2 (TCP) | lab3 (UDP) | lab4 (широковещание) |
|---|---|---|---|

## 8. Вопросы для самопроверки

1. **Почему широковещание возможно только в UDP?** TCP — протокол с установленным соединением: `connect` фиксирует адрес одного узла, а широковещательный адрес не может быть стороной соединения (раздел 3.15).
2. **Зачем `SO_BROADCAST`?** По умолчанию отправка на широковещательный адрес запрещена; опция снимает запрет, иначе `sendto` вернёт `SOCKET_ERROR` с `WSAEACCES`.
3. **Чем ограниченное широковещание отличается от направленного?** 255.255.255.255 адресует все узлы каждого локального сегмента, направленный (`192.168.31.255`) — только узлы конкретной подсети; маршрутизаторы широковещательные пакеты не пересылают.
4. **Почему на одной машине работают все три адреса?** Локальный стек получает и ограниченное широковещание, и направленное широковещание своей подсети, и широковещание петли `127.255.255.255` — проверено фактически.
5. **Что будет, если позывной не совпал?** Сервер игнорирует датаграмму и продолжает ожидание; клиент при чужом отклике возвращает `false` и обнуляет структуру адреса.
6. **Как обработать несколько откликов серверов?** Читать `recvfrom` в цикле до таймаута и собирать адреса в множество — так сделано в `CountServers`; для одиночного поиска клиент берёт первый отклик с правильным позывным.
7. **Почему приёмник привязывается к `INADDR_ANY`, а не к широковещательному адресу?** `bind` задаёт локальный адрес сокета, а не адрес назначения; для приёма широковещательных датаграмм достаточно `INADDR_ANY` и номера порта.
